# Growse v0.8.0 スコープ定義書

## 1. 文書概要

本書は、Growse v0.8.0で実装するHTML Form Controls、Form Submission、WebGo Fetch API、Cookie / Session、およびHTTP通信のSecurity Boundaryの範囲、完了条件、対象外を定義する。

v0.8.0は、v0.7.0のDOM mutation、Event、Formの基本操作、CSS Transition / Animation、Page Lifecycle、および同一Origin Resource Loadingが完成していることを前提とする。

JavaScript、Service Worker、WebView、および既存ブラウザエンジンは使用しない。

---

## 2. リリーステーマ

> **時間に沿って動く画面から、データと対話して状態を育てるWebアプリケーションへ。**

描画済みの画面を操作するだけでなく、利用者がFormへ入力し、HTTP Requestを送信し、ResponseをDOMへ反映し、Cookieを介してSessionを継続できるようにする。

Navigation、HTML Form Submission、WebGo Fetchは共通のHTTP Policy、Cookie Jar、Cancellation、および安全上限を使用する。通信結果によるDOM更新はv0.7.0のStyle、Layout、Animation、Paint、およびHit Testingへ安全に接続する。

---

## 3. 準拠基準

本書で明示した範囲について、次を基準とする。

- HTML Living StandardのForms、Form Control Infrastructure、Form Submission
- Fetch StandardのRequest、Response、Header、Redirect、CORS Protocol
- URL StandardのURL parsingとapplication/x-www-form-urlencoded
- RFC 9110 HTTP Semantics
- RFC 6265および6265bisのうち本書で定義するCookie範囲
- MIME Sniffing StandardのうちResponse Content-Typeの検証

Fetch APIのJavaScript Interfaceや各仕様全体への適合は宣言しない。仕様と実装判断が競合する場合は、対応範囲内のWHATWG仕様、RFC、およびWeb Platform Testsを優先する。

---

## 4. 目標

1. Textarea、Select、Checkbox、Radioを表示し、PointerとKeyboardで操作できる
2. Formのsuccessful controlsを収集し、GETまたはPOSTで送信できる
3. Constraint Validationにより不正な送信を防止し、利用者へ理由を表示できる
4. WebGoからHTTP Requestを送信し、Responseを安全に読み取れる
5. Request Header、Body、Redirect、Error、Cancellationを一貫した型で扱う
6. Navigation、Form Submission、WebGo Fetchで同じCookie Jarを共有する
7. Same-Origin Policyと限定的なCORSを適用する
8. Page遷移、reload、Runtime停止時にPage由来の通信を確実に中止する
9. loading、success、empty、validation error、network errorをDOMで表現できる
10. fake HTTP Serverだけで通信Testを決定的に実行できる

## 5. Form Controls

### 5.1 対応要素とType

- `<input type="text">`
- `<input type="password">`
- `<input type="email">`
- `<input type="url">`
- `<input type="number">`
- `<input type="checkbox">`
- `<input type="radio">`
- `<input type="hidden">`
- `<input type="submit">`
- `<button type="submit">`
- `<textarea>`
- `<select>` / `<option>`
- `<label>`
- `<form>`

未指定または未知の`input` typeは`text`として扱う。`file`、`date`、`time`、`color`、`range`などの専用Pickerはv0.8.0の対象外とする。

### 5.2 ValueとState

- `value`とdefault valueを区別する
- Checkbox / Radioの`checked`とdefault checkedを区別する
- Selectのsingle selectionと`selected`を扱う
- Radioは同じForm ownerと`name`を持つGroup内で1つだけ選択する
- `disabled`なControlと、disabledな`fieldset`配下を操作・送信対象から除外する
- `readonly`なText Controlは編集不可だが送信対象に含める
- `form.reset()`相当のWebGo操作でdefault stateへ戻す
- DOM attribute変更と利用者操作のstateを不用意に上書きしない

### 5.3 Interaction

- Pointerによるfocus、Checkbox切替、Radio選択、Select選択
- Tab / Shift+TabによるForm Control間のfocus移動
- SpaceによるCheckbox / Radio / Button操作
- EnterによるText Controlからのimplicit submission
- Textareaの複数行編集と改行
- `input`、`change`、`focus`、`blur`、`submit`、`reset` Event
- LabelのPointer操作による関連Controlへのfocusまたはactivation

Keyboard操作とPointer操作は同じDOM stateとEvent順序へ収束する。Controlの表示状態、Hit Testing、および送信値が食い違わないようにする。

## 6. Constraint Validation

### 6.1 対応Constraint

- `required`
- `minlength` / `maxlength`
- `min` / `max` / `step`（number）
- emailとURLの基本的なtype mismatch
- `pattern`のGo regexpで安全に表現できる範囲
- CheckboxとRadio Groupのrequired
- `novalidate`とSubmitterの`formnovalidate`

### 6.2 Validation結果

Controlごとに少なくとも次の状態を区別する。

- value missing
- type mismatch
- pattern mismatch
- too short / too long
- range underflow / overflow
- step mismatch
- valid

送信前にForm全体を検証し、最初のinvalid Controlへfocusを移す。ErrorはBrowser statusとControlの`:invalid` / `:valid` stateへ反映する。利用者が入力を修正した場合は再評価する。

任意文字列を指定する`setCustomValidity()`相当と、OS固有のValidation Bubble UIはv0.8.0の対象外とする。

## 7. Form Submission

### 7.1 Form OwnerとSubmitter

- Controlの祖先`form`または`form` attributeからForm ownerを解決する
- Submitに使用したButtonをSubmitterとして保持する
- `action`、`method`、`enctype`、`target`の既定値を適用する
- Submitterの`formaction`、`formmethod`、`formenctype`でForm設定を上書きする
- `submit` Eventがpreventされた場合はRequestを送信しない

`target`は`_self`だけを実行対象とする。未知のBrowsing Context名と`_blank`は新規Windowを作らず、明示的な未対応Errorとして扱う。

### 7.2 Entry List

DOM順にsuccessful controlsを収集する。

- `name`がないControlは除外する
- disabled Control、未選択Checkbox、未選択Radioは除外する
- 選択されたSubmitterだけを含める
- Selectは選択Optionの`value`またはTextを使用する
- Checkbox / Radioに`value`がない場合は`on`を使用する
- Textareaの改行はCRLFへ正規化する
- 同名Controlの複数値と空文字列を保持する

### 7.3 MethodとEncoding

- `method=get`はEntry ListをQueryへ`application/x-www-form-urlencoded`で追加してNavigationする
- `method=post`は`application/x-www-form-urlencoded` Bodyを送信してResponseへNavigationする
- UTF-8でpercent-encodingする
- GETでは既存Queryを仕様に沿って置換または結合する
- FragmentはHTTP Requestへ送信しない
- POST後のRedirectはRedirect policyに従う

`multipart/form-data`、`text/plain`、File upload、およびHTTP以外のSchemeへの送信はv0.8.0の対象外とする。

## 8. WebGo Fetch API

### 8.1 Packageと基本モデル

WebGoへ`growse/fetch` Packageを公開する。公開APIはGoの型としてRequest / Response / Headerを提供し、少なくとも次を表現できるものとする。

- URLまたはPage URLを基準にした相対URL
- Method
- Header
- `[]byte`またはUTF-8文字列のBody
- redirect mode
- credentials mode
- HTTP status、status text、final URL、redirected
- Response Header
- Response Bodyの`Bytes()`、`Text()`、`JSON()`相当

GET、HEAD、POST、PUT、PATCH、DELETEを許可する。Method token、Header name/value、およびBodyを送信できないMethodを検証し、不正値をRequest送信前にErrorとする。

### 8.2 実行モデル

- FetchはPage Runtimeに属する非同期Operationとして開始する
- 完了Callbackは対象PageのEvent Queueで直列実行する
- 1 Requestにつきsuccessまたはerrorのどちらかを1回だけ通知する
- CallbackからDOMを変更できる
- Page遷移、reload、Runtime停止時は未完了Requestをcancelする
- cancel後のResponseやCallbackを新しいPageへ配送しない
- 同じPageで複数Requestを並行実行できる

実装上goroutineを使用しても、DOMとRuntimeへのCallbackは同時実行しない。Testは実時間のsleepや通信完了順へ依存させない。

### 8.3 HeaderとBody

- Header名はASCII case-insensitiveとして扱う
- 複数値Headerを保持する
- `Content-Type`を明示できる
- JSON encode / decode helperを提供する
- 空Bodyとzero-length Bodyを区別する
- Response Bodyは1回だけ消費できる
- Content-Length超過、途中切断、Decode errorを区別する

`Host`、`Content-Length`、`Connection`、CookieなどBrowserが管理するforbidden request headerをWebGoから直接設定させない。

## 9. HTTP Lifecycle

### 9.1 Redirect

- 301、302、303、307、308を扱う
- 303はHEAD以外をGETへ変更する
- 301 / 302のPOSTは互換動作としてGETへ変更する
- 307 / 308はMethodとBodyを維持する
- 相対Locationを現在のResponse URLから解決する
- RedirectごとにCookie、Origin、credentials、CORSを再評価する
- Redirect loopと上限超過をErrorにする
- HTTPSからHTTPへのdowngradeをSecurity Errorとして拒否できるPolicyを持つ

### 9.2 Error Model

少なくとも次を区別する。

- invalid request
- DNS / connection / TLS error
- timeout
- canceled
- redirect error
- same-origin / CORS error
- response too large
- unsupported MIME / encoding
- body decode error

HTTP 4xx / 5xxはNetwork Errorにせず、statusを持つResponseとして返す。Error表示にはcredentialを含むURL、Cookie、Authorization、およびResponse Bodyの機密情報を露出しない。

### 9.3 Loading State

BrowserはNavigation、Form Submission、WebGo Fetchを区別して追跡する。Navigation中は既存Pageを直ちに破棄せず、成功したResponseをcommitする時点で切り替える。WebGo Fetch中は現在のPageを操作可能に保つ。

同じ操作の多重送信をBrowserが自動禁止せず、Demo側でButtonのdisabledやloading stateを表現できるようにする。

## 10. CookieとSession

### 10.1 Cookie Jar

- Browser instanceごとにin-memory Cookie Jarを持つ
- Navigation、Subresource、Form Submission、WebGo Fetchで共有する
- `Set-Cookie`のName、Value、Domain、Path、Expires、Max-Age、Secure、HttpOnly、SameSiteを解析する
- Host-only CookieとDomain Cookieを区別する
- Path matching、expiration、overwrite、deletionを扱う
- Request URLとcredentials modeに応じてCookie Headerを生成する
- Secure Cookieを平文HTTPへ送信しない
- HttpOnly CookieをWebGoから参照させない
- Public suffixまたは無関係なDomainへのCookie設定を拒否する

Cookieはprocess終了時に破棄する。Disk保存、Browser間共有、Cookie管理UIはv0.8.0の対象外とする。

### 10.2 SameSite

- `Strict`、`Lax`、`None`を区別する
- `SameSite=None`には`Secure`を要求する
- Same-site判定へschemeとregistrable domainを使用する
- Cross-site subrequestではStrict / Lax Cookieを送信しない
- Top-level safe navigationではLax Cookieを許可する

Third-party CookieのPartitioning、Storage Access API、CHIPSはv0.8.0の対象外とする。

## 11. Same-Origin PolicyとCORS

### 11.1 Origin

Originはscheme、host、effective portの組として比較する。URLのuserinfo、path、query、fragmentはOrigin比較に使用しない。

- NavigationとHTML Form SubmissionはHTTP(S)のcross-origin遷移を許可する
- WebGo Fetchは既定でsame-originに限定する
- credentials modeは`omit`、`same-origin`、`include`を扱う
- `Origin` HeaderはBrowserが生成する
- Response URLがRedirectでcross-originになった場合も再評価する

### 11.2 CORS

- CORS-safelisted Method、Request Header、Content-Typeを扱う
- 単純Requestへ`Origin`を付与し、`Access-Control-Allow-Origin`を検証する
- credential付きRequestではwildcard Originを拒否する
- 非単純RequestではOPTIONS preflightを実行する
- `Access-Control-Allow-Methods`と`Access-Control-Allow-Headers`を検証する
- Preflight成功結果を有効期限付きでmemory cacheする
- WebGoへ公開するResponse Headerをsafelisted Headerと`Access-Control-Expose-Headers`へ限定する
- CORS失敗時はResponse BodyとHeaderをWebGoへ渡さない

Private Network Access、CORP、COEP、COOP、CSP、Mixed Content仕様全体はv0.8.0の対象外とする。

---

## 12. Securityと安全上限

既存のResource Loaderと同じURL validation、timeout、MIME validation、およびcredential redactionをNavigation、Form Submission、WebGo Fetchへ適用する。

最低限、次の上限を設定可能な定数またはPolicyとして管理する。

- Pageあたりの同時WebGo Fetch数
- Browser全体の同時HTTP Request数
- Request Body size
- Response Body size
- Response Header countと合計size
- Redirect回数
- Cookie数、1 Cookie size、DomainあたりのCookie数
- Form Control数と送信Entry数
- Form encoded Body size
- JSON nestingまたはdecode対象size
- Request timeoutとidle timeout

上限超過時は対象Operationだけを失敗させ、Browser、他のPage処理、およびCookie Jarを破損させない。Response Bodyを上限まで無制限にmemoryへ読み込んでから判定せず、stream読取中に停止する。

WebGo Runtimeは引き続き信頼できないGoコードを安全に実行するSandboxではない。Fetch対応を理由に任意Hostへの無制限なnetwork accessを許可せず、Origin PolicyとBrowser設定を必ず通す。

## 13. PerformanceとLifecycle

- HTTP clientとTransportをRequestごとに作り直さない
- idle connectionを安全に再利用する
- Response Bodyを必ずcloseし、cancel時もgoroutineを残さない
- Page終了後にCallback、Timer、Body、Request contextへの参照を保持しない
- Cookie lookupを全Cookieの無制限な線形走査へ依存させない
- Form Controlの入力ごとにDocument全体を不必要に再構築しない
- Fetch完了による複数DOM mutationを1回の画面更新へまとめられる
- active AnimationとNetwork callbackが同じFrameに発生しても最新状態を一度だけ描画する

代表Workloadとして100件のForm Control serialization、1000件のCookie matching、および並行Fetch完了処理をbenchmarkし、時間とAllocationの基準値を記録する。

## 19. Growse v0.8.0の定義

> **HTML Form、WebGo Fetch、Cookie Session、およびOrigin Securityを共通のHTTP Lifecycleへ統合し、利用者の入力とServerのデータから状態を更新できるWebアプリケーションを独自基盤で実行できるブラウザ。**
