# Growse v0.9.0 スコープ定義書

## 1. 文書概要

本書は、Growse v0.9.0で実装するWebGo Scheduler、URL / History API、Web Storage、HTTP Cache、およびそれらをPage Lifecycleへ統合する範囲、完了条件、対象外を定義する。

v0.9.0は、v0.8.0のDOM mutation、CSS Transition / Animation、HTML Form、WebGo Fetch、Cookie、Same-Origin Policy、CORS、およびPage Event Queueが完成していることを前提とする。

JavaScript、Service Worker、WebView、および既存ブラウザエンジンは使用しない。

---

## 2. リリーステーマ

> **通信して更新するページから、時間・URL・永続状態を自ら管理できるWebアプリケーションへ。**

WebGoから一度きりのEventやHTTP Responseへ反応するだけでなく、将来の処理を予約し、現在URLをApplication Stateとして更新し、戻る・進むで状態を復元し、Browserを再起動しても利用者のデータを保持できるようにする。

Navigation、History traversal、Timer、Animation Frame、Fetch callback、およびStorage操作をPage Lifecycleと同じSecurity Boundaryへ統合する。HTTP Resourceは仕様に沿ってCacheし、通常Navigation、reload、強制reloadで一貫した再利用・再検証規則を適用する。

---

## 3. 準拠基準

本書で明示した範囲について、次を基準とする。

- HTML Living StandardのTimers
- HTML Living StandardのSession History and Navigation
- HTML Living Standardの`history`、`location`、`popstate`、`hashchange`
- HTML Living StandardのWeb Storage
- URL StandardのURL parsing、serialization、query、fragment
- Fetch StandardのHTTP-network-or-cache fetch
- RFC 9110 HTTP Semantics
- RFC 9111 HTTP Caching
- RFC 8246の`immutable` Cache Directive

JavaScriptの`Window`、Promise、Web IDL Interfaceをそのまま公開することや、各仕様全体への適合は宣言しない。WebGoにはGoの型、Callback、および`error`を使用し、仕様上の状態遷移、順序、Origin分離、Cache Semanticsを対応範囲内で維持する。

仕様と実装判断が競合する場合は、対応範囲内のWHATWG仕様、RFC、およびWeb Platform Testsを優先する。

---

## 4. 目標

1. WebGoから一回限りまたは反復するTimerを登録・解除できる
2. WebGoから次の描画FrameへCallbackを登録・解除できる
3. Timer、Frame、Network、DOM EventのCallbackをPage Event Queueで直列実行できる
4. 現在URLの構成要素を安全な型として参照・変更できる
5. Same-document NavigationとSession Historyを戻る・進むへ統合できる
6. Origin単位のLocal StorageとPage session単位のSession Storageを操作できる
7. Local StorageをBrowser再起動後も原子的かつ安全に復元できる
8. HTTP ResponseをFreshnessとValidatorに基づいて再利用・再検証できる
9. 通常Navigation、reload、強制reloadのCache挙動を区別できる
10. fake clock、fake profile、fake HTTP Serverだけで時間・永続化・Cache Testを決定的に実行できる

---

## 5. WebGo Scheduler

### 5.1 Packageと基本モデル

WebGoへ`growse/scheduler` Packageを公開する。公開APIはGoの型として少なくとも次のOperationを提供する。

- 一回限りのCallbackをDuration後に登録する
- 一定間隔でCallbackを登録する
- Timer IDを使用して登録済みCallbackを解除する
- 次の描画FrameへCallbackを登録する
- Frame Callback IDを使用して登録を解除する

DurationはGoの`time.Duration`で表現する。Timer IDとFrame Callback IDはPage内で一意なopaque valueとし、別Pageで生成されたIDを操作できない。

WebGoから標準`time` PackageをimportしなくてもDurationを組み立てられるよう、`growse/scheduler`は`Millisecond`と`Second`を公開する。

文字列を評価するTimer、任意Source Codeの遅延Compile、および動的`eval`相当は提供しない。SchedulerはGo Callbackだけを受け付ける。

### 5.2 Timer Semantics

- 負のDelayは0として扱う
- Timerは指定時刻より前には実行しない
- CPU負荷や他Callbackの実行により指定時刻より遅れることを許容する
- 同じdeadlineを持つTimerは登録順にEvent Queueへ追加する
- 反復TimerのCallbackを同時実行しない
- 処理遅延で複数Intervalを通過しても、過去分をburst実行せず現在時刻へ追いつく
- Callback内から自分自身または別Timerを解除できる
- 一回限りTimerはCallback実行直前にactive setから除去し、配送待ちに解除された場合は実行しない
- 反復TimerはCallback完了後も解除されていなければ次回を予約する
- 5段階を超えて入れ子になった短時間Timerには4ms以上のclampを適用する

Timerの現在時刻にはwall clockではなく単調増加Clockを使用する。System clockの補正、timezone変更、およびsleep復帰でTimerの順序を逆転させない。

### 5.3 安全上限

最低限、次を設定可能なPolicyとして管理する。

- Pageあたりのactive Timer数
- Pageあたりのactive Interval数
- 1 Event Loop turnで配送するTimer Callback数
- 許可する最大Duration
- Timer IDの採番上限と安全な再利用
- Callbackの連続実行によるUI starvationを防ぐ処理budget

上限超過時は新しい登録だけを失敗させ、既存Timer、Animation、Network処理、およびBrowser UIを停止させない。

## 6. Animation Frame

### 6.1 Frame Callback

Frame Callbackは次の描画更新前に一度だけ実行する。CallbackにはPage timeline上の単調増加timestampを渡す。

- 同一Frameの全Callback、CSS Animation、Paint、およびHit Testingは同じtimestampを参照する
- 1回のCallback登録につき1回だけ配送する
- Callback内で再登録したCallbackは原則として次Frameへ配送する
- Callback解除後は未配送Callbackを実行しない
- activeなCSS AnimationまたはFrame Callbackがある場合だけ次Frameを要求する
- Frame drop時に過去Frameを連続生成せず、最新timestampへ進める

Frame CallbackによるDOM mutationは同じFrameの更新へ可能な範囲でまとめる。Layout中やPaint中にWebGo Callbackを割り込ませず、DOM、Style、Layout、Paintの一貫性を維持する。

### 6.2 Timerとの違い

Timerは経過時間後のTask配送に使用し、Frame Callbackは描画直前の更新に使用する。Timer Callbackを固定FPS描画の代用として扱わない。

Frameが不要なBackground状態やWindowが描画不能な状態ではFrame Callbackを無制限に実行しない。v0.9.0ではPage Visibility APIを公開せず、停止または低頻度化のPolicyをBrowser側で適用する。

---

## 7. Event QueueとPage Lifecycle

Timer、Frame Callback、DOM Event、およびFetch CallbackはPage Runtimeへ同時に進入せず、Page Event Queueで直列実行する。

- 各Task source内のFIFO順を保持する
- 異なるTask source間に仕様以上の不要な全順序を保証しない
- 1つのCallbackが長時間実行されても別goroutineからDOMへ同時アクセスしない
- CallbackがDOMを複数回変更した場合は画面更新を可能な範囲でまとめる
- navigation開始時点では現在Pageを保持し、Navigation commit時に旧PageのSchedulerを停止する
- reload、Historyによるcross-document Navigation、Runtime停止時に旧PageのTimerとFrame Callbackをすべて解除する
- cancel後または旧Pageに属するCallbackを新しいPageへ配送しない
- same-document NavigationではPage Runtimeとactive Timerを維持する
- Browser終了時にScheduler goroutine、Timer、Callback参照を残さない

CallbackのpanicやRuntime Errorは該当CallbackのErrorとして報告し、Scheduler内部Lockを保持したままBrowserを停止させない。WebGo Runtime自体が安全なSandboxではないという既存制約は変わらない。

## 8. URLとLocation

### 8.1 WebGo Navigation API

WebGoへ`growse/navigation` Packageを公開する。現在Documentに結び付いたLocation情報として少なくとも次を参照できるものとする。

- 完全なURL
- scheme
- host
- hostname
- effective port
- path
- query
- fragment
- origin

URLはURL Standardに従ってparse・resolve・serializeする。相対URLは現在DocumentのURLを基準に解決し、userinfoを含むURLをWebGo ErrorやBrowser statusへ表示するときはcredentialを伏せる。

### 8.2 Location変更

少なくとも次の操作を扱う。

- 新しいURLへNavigationする
- 現在History entryを置換してNavigationする
- 現在Documentをreloadする
- path、query、fragmentを変更する

fragmentだけが変わる場合はDocumentを再取得せずsame-document Navigationとして扱う。pathまたはqueryの変更は、History APIによるsame-document更新を明示した場合を除き通常のNavigationを行う。

HTTP(S)以外のScheme、空Host、無効なport、およびBrowser Policyで禁止されたURLはcommit前に拒否する。`javascript:`、`data:`、`file:`、custom schemeはv0.9.0のNavigation対象外とする。

---

## 9. Session HistoryとRouting

### 9.1 History Entry

History entryは少なくとも次を保持する。

- serialized URL
- same-document / cross-documentの種別
- WebGoが設定したstate
- scroll position
- Documentに対応するPage識別子

WebGo stateはUTF-8 JSONとして扱い、Go固有Pointer、Function、Channel、循環参照などを保存しない。無効なJSONまたはsize上限を超えるstateはHistoryを変更せずErrorを返す。

### 9.2 History操作

`growse/navigation`は少なくとも次の操作を提供する。

- 新しいsame-document entryを追加する
- 現在entryのURLとstateを置換する
- 指定deltaだけHistoryを移動する
- 戻る
- 進む
- 現在のentry数とstateを参照する

Historyへ追加・置換できるURLは現在Documentとsame-originでなければならない。cross-origin URL、credential付きURL、および無効URLを指定した場合はHistoryを変更しない。

新しいentryを追加した場合はforward historyを破棄する。置換ではentry数を増やさない。same-document History操作はHTTP Request、Document再parse、WebGo Runtime再起動を行わない。

### 9.3 Event

WebGoへ少なくとも次を配送する。

- History traversal後の`popstate`相当Event
- fragment Navigation後の`hashchange`相当Event

`popstate`相当Eventには移動先entryのstateを渡す。`hashchange`相当Eventにはcredentialを除去したold URLとnew URLを渡す。

entryの追加・置換そのものでは`popstate`を発生させない。History APIによるURL更新では`hashchange`を発生させず、LinkやLocation操作によるfragment Navigationと区別する。

Back / Forwardがcross-document entryへ移動する場合は既存Navigation Lifecycleを使用する。Back-Forward CacheによるPage全体の凍結・復元はv0.9.0の対象外とする。

---

## 10. Web Storage

### 10.1 PackageとData Model

WebGoへ`growse/storage` Packageを公開し、Local StorageとSession Storageを明示的に区別する。

各Storageは少なくとも次の操作を提供する。

- keyに対応するvalueを取得する
- keyとvalueを設定する
- keyを削除する
- すべてのentryを削除する
- entry数を取得する
- indexからkeyを取得する

keyとvalueはUTF-8文字列として扱う。存在しないkeyと空文字列のvalueを区別する。既存keyの更新では列挙順を不用意に変更せず、削除後の再追加は新しいentryとして扱う。

Go APIはQuota超過、無効Origin、I/O failure、および破損Storageを`error`として区別できるものとする。

### 10.2 Origin分離

Storage namespaceはscheme、host、effective portからなるOriginで分離する。

- 異なるscheme、host、port間でStorageを共有しない
- URLのpath、query、fragmentはStorage namespaceへ使用しない
- HTTPとHTTPSのStorageを分離する
- opaque OriginとHTTP(S)以外のOriginへStorageを公開しない
- WebGoから任意OriginのStorageを指定させない
- History APIでURLを変更してもsame-origin内では同じStorageを使用する
- cross-origin Navigation後は新しいOriginのStorageだけを公開する

Origin keyとFile pathの対応にはhashまたは安全なencodingを使用し、Host文字列を未検証のままDirectory traversal可能なpathへ変換しない。

### 10.3 Local Storage

Local StorageはBrowser profileへ永続化し、正常終了だけに依存せず次回起動時に復元できるものとする。

- 書き込みは原子的にcommitし、途中終了で既存の正常Dataを部分上書きしない
- 永続形式にschema versionを持たせる
- 一部Originの破損で他OriginのStorageを読み込めなくしない
- 未知versionや破損Dataを検出し、安全に隔離または初期化できる
- File permissionを可能な範囲で利用者だけに制限する
- Testでは実Profileを使用せず一時Directoryを注入できる

Local Storageは秘密情報の保管庫ではない。暗号化Storage、OS Keychain統合、およびcredential保存APIは提供しない。

### 10.4 Session Storage

Session StorageはPage sessionに属するmemory-only Storageとして扱う。

- same-document Navigationとreloadでは維持する
- 同じPage session内のBack / Forwardで維持する
- 新しいBrowser processでは空にする
- cross-origin NavigationではOriginごとのnamespaceを切り替える
- Browser終了時にDiskへ永続化しない

Growseはv0.9.0で複数Tabや子Windowを提供しないため、Page sessionのclone、opener連携、およびTab間Storage Eventは対象外とする。

---

## 11. Profileと永続化Lifecycle

Browser profileはLocal StorageとHTTP Cacheを独立した領域へ保存する。Storage Dataと破棄可能なCache Dataを同じFileやDirectoryへ混在させない。

- Local StorageにはOS標準のApplication Data Directory、HTTP CacheにはCache Directoryを使用する
- Testとportable実行向けにData rootとCache rootを個別に注入できる
- 相対path、symlink、permission、Directory作成Errorを明示的に扱う
- 同じprocess内の同時操作を直列化またはtransaction化する
- Disk full、read-only filesystem、rename failureでも既存Dataを破損させない
- 一時Fileと古いCache entryを安全に回収する
- LogへStorage value、History state、Cookie、Authorizationを出力しない

複数Growse processによる同一Profileの同時更新は、排他Lockで安全に拒否または単一writerとして扱う。後勝ちで無言上書きしてはならない。

---

## 12. HTTP Cache

### 12.1 対象RequestとCache Key

Navigation、Stylesheet、Image、外部WebGo Source、およびWebGo Fetchは共通のprivate HTTP Cache Policyを使用する。

- HTTP(S)のGETとHEADをCache対象とする
- Method、Request URL、および`Vary`対象Request HeaderからCache keyを構成する
- SubresourceとFetchではtop-level Origin、Navigationでは遷移先Originをpartition keyへ含める
- URL fragmentをCache keyへ含めない
- credentialを含むURLをそのままDisk file名やLogへ使用しない
- `Vary: *`を再利用不可として扱う
- CORS ResponseはCache hit時も現在RequestのOriginとcredentials modeで再評価する
- Redirect後は最終Responseと各RedirectのCache可能性を個別に判定する

POST、PUT、PATCH、DELETEのResponse再利用、Range Cacheの結合、およびStreaming partial entryはv0.9.0の対象外とする。

### 12.2 Freshness

少なくとも次のResponse DirectiveとHeaderを扱う。

- `Cache-Control: max-age`
- `Cache-Control: no-cache`
- `Cache-Control: no-store`
- `Cache-Control: private`
- `Cache-Control: public`
- `Cache-Control: must-revalidate`
- `Cache-Control: immutable`
- `Expires`
- `Date`
- `Age`
- `Vary`

`s-maxage`はshared cache向けDirectiveであるため、Growseのprivate cacheでは適用しない。

明示的なFreshness情報を優先し、現在Ageをoverflowなく計算する。明示的FreshnessがないResponseへのheuristic cachingは、`Last-Modified`を使用する限定的な範囲だけを対象とし、計算規則と上限を文書化する。

`no-store` ResponseはmemoryとDiskのどちらにも保存しない。`no-cache` Responseは保存を許可するが、再利用前に必ず再検証する。未知Directiveは既知Directiveの評価を壊さず無視する。

### 12.3 Validatorと304

stale entryまたは再検証が必要なentryに対して、次を扱う。

- `ETag`と`If-None-Match`
- `Last-Modified`と`If-Modified-Since`
- `304 Not Modified`

両方のValidatorが存在する場合は`ETag`を優先し、仕様に従って条件付きRequestを構築する。304 Response受信時は保存済みBodyを再利用し、更新可能なHeader、Freshness、およびAge情報をmergeする。

304だけをBodyのない通常ResponseとしてPageへcommitしない。保存済みentryがない不正な304、Validator不一致、および破損BodyはCache missまたは明示的Errorとして安全に処理する。

### 12.4 Disk Cache

Cache可能なResponseはsizeとPolicyの範囲内でBrowser profileのCache領域へ保存できる。

- MetadataとBodyの対応をchecksumまたは同等の方法で検証する
- 書き込み途中のentryをCache hitとして公開しない
- Cache schema versionを管理する
- 破損entryだけを破棄し、Cache全体やLocal Storageを破損させない
- entry数、1 Response size、Origin単位size、全体sizeへ上限を設ける
- 容量超過時は使用時刻とsizeに基づく決定的なevictionを行う
- `Authorization`を含むRequestまたは`Set-Cookie`を含むResponseはv0.9.0でDiskへ永続化しない

HTTP Cacheは破棄可能Dataであり、削除されてもApplicationの永続Dataを失わない。Local Storageと同じ耐久性を保証しない。

## 13. Reload、Invalidation、Failure

### 13.1 NavigationとReload

- 通常Navigationはfresh entryを再利用できる
- 通常reloadはDocumentを再検証し、ResourceごとのCache Directiveを尊重する
- 強制reloadはfresh entryも無条件に使用せず、DocumentとSubresourceへ再検証を要求する
- `no-store` entryをreload後に残さない
- 304による再検証成功時はHistory entryを増やさない
- Cache hitでもNavigation、MIME validation、Origin Policy、およびPage commit規則を省略しない

Network Error時にstale Responseを暗黙利用しない。`stale-if-error`による再利用はv0.9.0の対象外とする。

### 13.2 Invalidation

同一URLへ状態変更Methodが成功した場合は、そのURLに対応するCache entryを無効化する。`Location`または`Content-Location`がsame-origin URLを示す場合は、仕様で許される範囲で関連entryも無効化する。

WebGo Storage更新でHTTP Cacheを削除せず、HTTP Cache evictionでLocal StorageやHistory stateを削除しない。

### 13.3 Error Model

少なくとも次を区別する。

- Cache miss
- stale entry
- validation failure
- corrupt entry
- unsupported cache metadata
- quota / disk full
- permission error
- profile lock conflict

Cache自体の読取失敗は、Network Requestが可能ならCache missとして回復できる。DiskへのCache保存失敗だけを理由に取得済みの正常ResponseをPageへ渡さない動作にはしない。

---

## 14. Securityと安全上限

Scheduler、History、Storage、CacheはすべてPageとOriginに属するResourceとして管理する。

最低限、次の上限を設定可能な定数またはPolicyとして管理する。

- PageあたりのTimer / Interval / Frame Callback数
- 1 turnあたりのCallback数と実行budget
- History entry数
- 1 History state sizeとSession全体のstate size
- Storage key / value size
- OriginあたりのLocal / Session Storage容量
- Profile全体のStorage容量
- Cache entry数、1 entry size、Origin単位size、全体size
- `Vary` Header数とCache key size
- Cache metadata sizeと304 merge回数
- Profile pathと一時File数

上限判定前に無制限なDataをmemoryへ読み込まない。整数overflow、Duration overflow、巨大JSON、巨大Header、長大URL、path traversal、symlink差し替え、破損Metadata、およびCache decompression bombがpanic、hang、busy loop、任意File上書きを発生させないようにする。

StorageとCacheを追加してもWebGo Runtimeは信頼できないGoコードを安全に実行するSandboxにはならない。既存のtrusted localhost制約とOrigin Policyを維持する。

---

## 15. PerformanceとLifecycle

- Timerごとに永続goroutineを1つ生成せず、deadline順に管理する
- 次deadlineがない場合はSchedulerをbusy loopさせない
- cancel済みTimerと終了PageへのCallback参照を速やかに解放する
- 同一Frameの複数CallbackによるDOM mutationを1回のStyle / Layout更新へまとめる
- History traversalをentry数の無制限な全走査へ依存させない
- Local Storageの読取を毎回Disk scanへ依存させない
- 1 keyの更新で全OriginのStorageを書き直さない
- Cache lookupをCache全体の無制限な線形走査へ依存させない
- fresh Cache hitでNetwork接続を開始しない
- 304再検証で保存済みBodyを不要に複製しない
- evictionとcleanupをUI threadで無制限に実行しない

代表Workloadとして10,000 Timerの登録・解除、1,000 History entryのtraversal、10,000 Storage entryのlookup / update、および1,000 Cache entryのhit / revalidationをbenchmarkし、時間とAllocationの基準値を記録する。

## 16. テスト方針

### 16.1 Unit Test

- Timer登録、解除、deadline、同時刻順序、Interval再予約
- 負Delay、nested clamp、Duration overflow、Timer上限
- Frame Callbackの一回配送、解除、timestamp共有
- URL parse、resolve、serialize、Origin比較、credential redaction
- History entry追加・置換・forward破棄・delta traversal
- `popstate` / `hashchange`相当Eventの発生条件と順序
- Storage key順、空value、更新、削除、clear、quota
- OriginごとのLocal / Session Storage分離
- Local Storageのatomic commit、schema version、破損復旧
- Cache-Control、Age、Expires、Vary、Freshness計算
- ETag / Last-Modified再検証と304 Header merge
- Cache invalidation、eviction、corrupt entry、size上限

### 16.2 Integration Test

- Timer CallbackによるDOM更新とCSS Transition開始
- Intervalの解除とPage終了後のCallback抑止
- Frame Callback、CSS Animation、Paintのtimestamp一致
- Fetch、Timer、DOM Eventが同じPage Queueで直列実行されること
- query / fragmentを使ったsame-document Routing
- Historyの戻る・進むによるURL、state、scroll位置の復元
- reloadとcross-document NavigationにおけるScheduler破棄
- Local StorageのBrowser再起動相当の復元
- Session Storageのreload維持と新規sessionでの破棄
- fresh Cache hit、stale再検証、304 Body再利用
- Navigation、Stylesheet、Image、WebGo Source、FetchのCache共有
- 通常reloadと強制reloadのRequest Headerおよび再利用差
- Disk failure、破損Cache、quota超過からの局所的回復

Testはfake clock、fake frame source、一時Profile Directory、`httptest.Server`、および注入可能なTransportを使用する。実時間のsleep、利用者の実Profile、Public Internet、外部DNS、実在Serviceへ依存しない。

### 16.3 Visual Regression

Persistent App Showcaseの初期表示、復元済み状態、Routing後、保存中、保存済み、Cache再検証中、およびError状態を固定Viewport / Font / Scale / timestampでSnapshot化する。

History traversal後のscroll位置と、Frame Callbackで更新したDOMのPaint結果を決定的に記録する。

### 16.4 Conformance Test

HTML Timers、Session History、Navigation、Web Storage、URL、およびHTTP Cacheに関するWeb Platform Testsまたは仕様Testから対応Featureに必要なTestを選定し、出典、固定revision、縮約内容、未対応理由を`docs/wpt.md`へ記録する。
