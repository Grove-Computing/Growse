# Growse v0.10.0 スコープ定義書

## 1. 文書概要

本書は、Growse v0.10.0で実装するBrowser Session、複数Tab、左側のVertical Tab UI、Tab単位のPage Lifecycle、およびTab間で共有するProfile Resourceの範囲、完了条件、対象外を定義する。

v0.10.0は、v0.9.4までのWebGo Scheduler、URL / History API、Web Storage、HTTP Cache、Form、Fetch、Cookie、Same-Origin Policy、CORS、およびPage Lifecycleが完成していることを前提とする。

JavaScript、Service Worker、WebView、および既存ブラウザエンジンは使用しない。

---

## 2. リリーステーマ

> **一つのWebアプリを開くブラウザから、複数のページを縦タブで安全に行き来できるブラウザへ。**

利用者は現在Pageを破棄せずに別のWebアプリを開き、左側のVertical Tab RailからPageを切り替えられる。各Tabは独立したURL、History、Scroll、Focus、WebGo Runtime、Scheduler、およびSession Storageを保持しながら、同じBrowser Sessionに属するLocal Storage、Cookie、およびHTTP Cacheを仕様の範囲内で共有する。

Chromeなどで一般的なWindow上部のHorizontal Tab Stripは採用しない。Growse v0.10.0のTab UIは、Page Viewportの左側へ常設するVertical Tab Railを唯一の標準配置とする。

---

## 3. 準拠基準

本書で明示した範囲について、次を基準とする。

- HTML Living StandardのBrowsing Context、Top-level Traversable、Choosing a Browsing Context
- HTML Living StandardのNavigationとSession History
- HTML Living StandardのPage Lifecycleに関係するEvent LoopとTimer
- HTML Living StandardのPage VisibilityにおけるBackground Pageの考え方
- Web Storage StandardのStorage AreaとStorage Event
- Fetch StandardのOrigin、Credentials、Fetch Lifecycle
- RFC 6265bisのCookie Storage ModelとCookie送信規則
- RFC 9110 HTTP Semantics
- RFC 9111 HTTP Caching

WebGoへJavaScriptの`Window`、`WindowProxy`、`document.visibilityState`、Promise、およびWeb IDL Interfaceをそのまま公開しない。仕様全体への適合は宣言せず、本書で明示したTab選択、Browsing Context分離、Lifecycle、Storage通知、およびProfile共有の範囲に限定する。

## 4. 目標

1. 1つのBrowser Windowで複数のTop-level Pageを保持できる
2. Page左側のVertical Tab RailからTabを作成、選択、終了できる
3. KeyboardだけでTabの作成、終了、前後切替を実行できる
4. 各TabのNavigation、History、Scroll、Focus、Runtime、および非同期処理を分離できる
5. Background Tabの描画処理を抑制しながらPage Stateを維持できる
6. Local Storage、Cookie、およびHTTP CacheをBrowser Session内で安全に共有できる
7. Session StorageをTabごとのPage Sessionとして分離できる
8. Tab終了、Navigation競合、およびBrowser終了で旧Pageの処理を確実にcancelできる
9. Tab数、Background Callback、通信、および表示文字列へ安全上限を適用できる
10. fake Navigator、fake Clock、一時Profile、およびfake HTTP Serverだけで複数TabのTestを決定的に実行できる

## 5. Browser SessionとTab Model

### 5.1 Browser Session

Browser Windowごとに1つのBrowser Sessionを持つ。Browser Sessionは順序付きTab Collection、現在選択中のTab、共有Profile Resource、およびSession全体のResource Policyを所有する。

各Tabは少なくとも次の状態を持つ。

- Session内で一意なopaque Tab ID
- Tabの作成順と現在の表示順
- active / background / closing / closedのLifecycle State
- Tab固有のBrowser、Page、Navigation ID、およびHistory
- 表示用Title、credentialを除去したURL、Loading State、Error State
- 最終選択時刻と未描画Mutationの有無

Tab IDは再利用によって遅延CallbackやNavigation Resultを別Tabへ誤配送しない。採番上限へ到達した場合は新しいTab作成を安全に拒否し、既存Tabを維持する。

### 5.2 Tab Operation

Browser Sessionは少なくとも次のOperationを提供する。

- 空のTabを末尾へ作成する
- URLを指定して新しいTabを作成する
- Tab IDまたは表示位置からTabを選択する
- 現在Tabの次または前のTabを循環選択する
- 指定Tabを終了する
- Tab一覧、active Tab、およびTab数をread-onlyに取得する

同時にactiveとなるTabは必ず1つとする。最初のTab作成時はそのTabをactiveにする。active Tabを終了した場合は右隣、右隣がなければ左隣を選択する。最後のTabを終了した場合はBrowser Windowを終了せず、空の新規Tabを1つ作成してAddress BarへFocusする。

Tabの並べ替え、固定、Group化、および別Windowへの移動はv0.10.0では提供しない。

### 5.3 Session Safety

既定の最大Tab数は64とし、設定可能なPolicyとして管理する。Tab作成失敗でactive Tab、Tab順序、および共有Profile Stateを変更しない。

TitleはUTF-8として検証し、表示と保持は4 KiBまでとする。長いTitleとURLはVertical Tab Rail内で省略し、Layout、Memory、およびLogを無制限に増加させない。credential付きURLはTab Label、Status、Error、およびLogへ表示しない。

## 6. Vertical Tab UI

### 6.1 配置

Tab UIはBrowser Windowの左側へ縦方向に配置し、ToolbarとPage Viewportの上へ重ねない。上部Horizontal Tab Stripは作成しない。

Vertical Tab Railは少なくとも次を表示する。

- 新規Tabを作成するButton
- 各TabのTitleまたはHost fallback
- active Tabの明確な選択状態
- Loading、Error、および未描画更新の状態
- 各Tabを終了するButton

Tab RowはDOMの一部ではなくBrowser Chromeとして描画し、閲覧PageのCSS、Hit Testing、およびWebGo DOM Eventから分離する。Page側の`position: fixed`、高い`z-index`、Transform、およびPointer EventでTab Railを覆ったり操作したりできない。

### 6.2 Layout

Vertical Tab Railの既定幅は224 dpとする。Window幅が狭い場合もTab RailとPage ViewportのGeometryを明示的に分け、負Size、重なり、無限Layout、およびHit Testingの座標ずれを発生させない。

Tab数が表示高を超える場合はTab Railだけを縦Scrollできる。Tab RailのScrollはPage Scroll、Historyへ保存するScroll位置、およびPage Hit Testingへ影響させない。

v0.10.0ではTab Railの幅変更、折り畳み、右側配置、および利用者による配置変更を対象外とする。

### 6.3 Input

少なくとも次の操作を提供する。

- Tab RowのclickでTabを選択する
- Close Buttonで対象Tabを終了する
- New Tab Buttonで空Tabを作成する
- `Ctrl+T`、macOSでは`Command+T`で空Tabを作成する
- `Ctrl+W`、macOSでは`Command+W`でactive Tabを終了する
- `Ctrl+Tab`で次のTab、`Ctrl+Shift+Tab`で前のTabを選択する

Keyboard ShortcutはForm Controlへの通常入力を不必要に奪わず、Browser ChromeのShortcutとして処理する。Key repeatによるTab大量作成、既にclosedのTabへの連続Close、および同時clickを安全に直列化する。

## 7. Tab Navigation

### 7.1 Navigationの宛先

Address Bar、Back、Forward、Reload、強制Reload、およびWebGo Navigation APIは、Operation開始時にactiveだったTabを宛先として固定する。Operation完了前に別Tabへ切り替えても、Navigation Resultを新しいactive Tabへ誤ってcommitしない。

各Tabは同時に1つのNavigationだけをcommit候補として保持する。同じTabで新しいNavigationを開始した場合は古いNavigationをcancelし、遅れて完了したResponse、Script、Image、およびCallbackを破棄する。別TabのNavigationは相互にcancelしない。

Background TabでNavigationが完了した場合はPage Stateを更新するが、自動的にactive Tabへ切り替えない。LoadingとErrorは対象Tab Rowへ反映する。

### 7.2 新しいTabを開くNavigation

少なくとも次の利用経路を扱う。

- New Tab ButtonまたはShortcutで空Tabを開く
- Linkの`target="_blank"`を利用者のclickから新しいTabへ開く
- Formの`target="_blank"`または`formtarget="_blank"`をSubmissionから新しいTabへ開く
- Browser Chromeから現在URLを新しいTabへ開く

新しいTabはactiveとして開く。`_blank`で作成したTabへ元PageのRuntime参照やDOM参照を渡さず、暗黙に`noopener`相当として扱う。任意の名前付きBrowsing Context、`window.open()`相当、および利用者操作を伴わないPopup作成は提供しない。

### 7.3 HistoryとAddress Bar

Back / Forwardの可否、Address BarのURL、Reload、およびStatus表示はactive Tabだけを参照する。Tab切替時に選択先TabのURL、History State、Title、Scroll、およびLoading StateをBrowser Chromeへ同期する。

History entryをTab間で共有しない。Tabを終了した後に、そのHistoryからPageを復元できない。Duplicate TabとSession Restoreを提供しないため、HistoryのcloneとDisk永続化はv0.10.0の対象外とする。

## 8. Per-Tab Page Lifecycle

### 8.1 分離するResource

各Tabは少なくとも次を独立して所有する。

- 現在PageとSession History
- WebGo RuntimeとPage Event Queue
- Timer、Interval、およびAnimation Frame Callback
- 実行中NavigationとWebGo Fetch
- DOM、Style、Layout、Paint、およびHit Testing State
- Hover、Focus、Form editor、およびScroll State
- Session StorageのPage Session

あるTabのRuntime Error、Callback panic、Navigation Error、invalid DOM mutation、およびStorage Errorで、別TabまたはBrowser Session全体を終了させない。

### 8.2 Tab切替

Tabをbackgroundへ移してもPage、History、DOM、Runtime、およびSession Storageを破棄しない。activeへ戻したときは保存済みScroll、Focus、Form入力、およびLayout Stateを復元する。

Background TabではAnimation Frame CallbackとCSS AnimationのFrame生成を停止する。再選択時はPage timelineの現在timestampを1回評価し、停止中の過去Frameをburst生成しない。

Background TabのTimerには1秒以上のclampを適用し、1 turnあたりのCallback数を制限する。FetchとNavigationはbackgroundでも完了可能とするが、CallbackをそのTab固有のPage Event Queueで直列実行する。Background TabのMutationはそのTabだけをdirtyとして記録し、active TabのLayoutやPaintを起動しない。

Page Visibility API自体をWebGoへ公開することはv0.10.0の対象外とする。

### 8.3 Tab終了

Tab終了時は次を順序付けて実行する。

1. Tabをclosingとして新規Operationを拒否する
2. Navigation、Fetch、Timer、Interval、Frame Callbackをcancelする
3. Page Event Queueへの新規配送を停止する
4. WebGo RuntimeとCallback参照を解放する
5. Session StorageとHistoryを破棄する
6. TabをCollectionから除去する

close開始後のCallback、Navigation Result、Storage Event、およびFrameをclosed Tabへ配送しない。Browser Window終了時はすべてのTabへ同じ終了処理を適用し、goroutine、Timer、Response Body、Runtime参照、および一時Fileを残さない。

## 9. Shared Profile State

### 9.1 Local Storage

同じBrowser Session内のTabは、同じscheme、host、およびeffective portに対して同じLocal Storage Areaを参照する。別Origin、別Profile、および別Browser Sessionの値を混在させない。

Local Storage更新が原子的にcommitされた後、更新を行ったTab以外のsame-origin TabへStorage Event相当のWebGo Eventを配送する。Eventはkey、old value、new value、clearの種別、およびcredentialを除去した更新元URLを持つ。異なるOrigin、closed Tab、および更新元Tabへ配送しない。

複数Tabから同時に更新された場合はStorage Managerでcommit順を確定し、その順序でEventを配送する。quota、Disk Error、schema Error、またはatomic commit失敗時はEventを配送しない。

### 9.2 Session Storage

Session StorageはTabのPage Sessionごとに分離する。同じOriginを開いた別Tabであっても値を共有しない。same-document Navigation、reload、および同じTabのBack / Forwardでは維持し、Tab終了時に破棄する。

Duplicate Tabと`window.open()`を提供しないため、Session Storageのcloneは行わない。Session Storage更新によるTab間Storage Eventも配送しない。

### 9.3 Cookie

Navigation、Form Submission、およびWebGo Fetchが使用するCookie JarをBrowser Sessionで共有する。同じCookieのDomain、Path、Secure、HttpOnly、SameSite、およびExpiration規則をすべてのTabへ一貫して適用する。

Cookieを受信したTabに関係なく、後続の適格なRequestで共有Cookieを使用できる。Requestごとのtop-level URL、Origin、Method、およびCredentials Modeを使って送信可否を再評価し、あるTabのCORS結果やcredentials判断を別Tabへ流用しない。

CookieのDisk永続化、管理UI、Partitioned Cookie、およびPublic Suffix List全体はv0.10.0の対象外とする。

### 9.4 HTTP Cache

同じBrowser SessionのTabは同じprivate HTTP Cacheを共有する。fresh entry、Validator、304 merge、Vary、partition key、quota、およびDisk Cacheの既存規則を維持する。

Cache hit時も各TabのRequest ContextでMIME、Origin、CORS、およびCredentials Policyを再評価する。同時Requestの完全なRequest Coalescingは要求しないが、同一entryへの同時書き込みでMetadata、Body、LRU、およびchecksumを破損させない。

Tab終了によって共有Cacheを削除しない。Browser Session終了時もDisk Cacheは破棄可能なProfile Dataとして既存Policyに従って保持できる。

## 10. Securityと安全上限

TabはSecurity Boundaryを緩和する共有単位ではない。Origin Policy、CORS、Cookie、Storage、およびCache partitionはRequestまたはResourceごとに評価する。

v0.10.0では最低限、次の上限を設定可能なPolicyとして管理する。

- Browser SessionあたりのTab数
- Tab IDの採番上限
- active / background TabあたりのTimer、Frame Callback、Fetch数
- Session全体の同時NavigationとFetch数
- Background TabのTimer clampと1 turnあたりCallback数
- Tab Title、URL、Status、およびError表示の長さ
- Tab Railが保持するLayout、Icon、およびInput State数
- Tab終了時に待機するcancelとcleanupの時間

既定値はTab 64件、Tabごとの同時Fetch 16件、Session全体の同時Fetch 128件、Background Timer最小1秒、Background Tab 1 turnあたり100 Callback、Title 4 KiB、表示URL 8 KiBとする。

上限超過時は新しいOperationだけを失敗させ、既存Tab、active Page、共有Storage、およびBrowser Chromeを停止させない。巨大Title、長大URL、Tab大量作成、Shortcut key repeat、遅延Navigation Result、およびclose競合がpanic、hang、busy loop、情報漏えいを発生させないようにする。

WebGo Runtimeが信頼できないGoコードを安全に実行するSandboxではないという既存制約は変わらない。Tab分離をProcess SandboxやSite Isolationとして説明しない。

## 11. Performance

- Background TabのDOM、Style、Layout、Paintを毎Frame再計算しない
- Tab切替を全TabのDocument再parseやResource再取得へ依存させない
- Tab Row描画をPage DOMのNode数へ依存させない
- Tab RailのScrollでPage Layoutを再構築しない
- 1 TabのMutationで全TabのLayout Cacheを破棄しない
- inactive TabのAnimation Frameをbusy loopさせない
- Local Storage Event配送を異なるOriginの全Tab走査へ無制限に依存させない
- Tab終了時にSession全体のLocal Storage、Cookie、およびHTTP Cacheを複製または破棄しない
- Tab切替とcloseでRuntime、Editor、およびLayout参照を蓄積しない

代表Workloadとして64 Tabの作成・切替・終了、64 Background Tabを含むFrame更新、16 TabからのLocal Storage更新、および共有HTTP Cache hitをbenchmarkし、時間とAllocationの基準値を記録する。

## 12. テスト方針

### 12.1 Unit Test

- Tab ID、作成順、active選択、前後循環、close後の選択
- 最大Tab数、ID上限、長大Title、無効URL
- active TabとBrowser Chrome Stateの同期
- TabごとのHistory、Scroll、Focus、Runtime、Session Storage分離
- Background Timer clamp、Frame停止、再選択時のtimestamp
- close中とclosed TabへのCallback、Navigation Result、Storage Event抑止
- Local Storage共有とcommit順のStorage Event配送
- Cookie Jar共有とTabごとのSameSite / Credentials再評価
- HTTP Cache共有と同時書き込み

### 12.2 Integration Test

- Vertical Tab RailからTabを作成、切替、終了する
- ShortcutだけでTabを作成、前後切替、終了する
- `target="_blank"`のLinkとFormを新しいTabへNavigationする
- 複数TabのNavigation完了順が入れ替わっても正しいTabへcommitする
- Background TabのDOM mutationがactive TabのPaintを変更しない
- Tab切替後にHistory、Scroll、Focus、Form値を復元する
- same-origin Tab間でLocal StorageとCookieを共有する
- cross-origin Tab間でStorageとSecurity Stateを分離する
- Tab終了とBrowser終了後にTimer、Fetch、Runtime参照を残さない

Testはfake Navigator、fake Clock、fake Frame Source、一時Profile Directory、`httptest.Server`、および注入可能なTransportを使用する。実時間のsleep、Public Internet、外部DNS、利用者の実Profile、およびOS固有Window操作へ依存しない。

### 12.3 Visual Regression

固定Viewport、Font、Scale、およびtimestampで少なくとも次をSnapshot化する。

- 左側Vertical Tab Railとactive Tab
- 複数Tabの通常、Loading、Error状態
- Tab数が表示高を超えたScroll状態
- 長いTitleとURLの省略
- active Tab切替後のPage Viewport、Scroll、およびGopher Cursor
- 狭いWindowでTab RailとPageが重ならない状態

Horizontal Tab Stripが上部へ生成されていないこともGeometry Snapshotで検証する。

### 12.4 Conformance Test

Browsing Context、`target="_blank"`、Page Lifecycle、Storage Event、Cookie、およびHTTP Cacheに関するWeb Platform Testsまたは仕様Testから対応Featureに必要なTestを選定し、出典、固定revision、縮約内容、および未対応理由を`docs/wpt.md`へ記録する。
