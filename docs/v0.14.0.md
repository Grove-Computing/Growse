# Growse v0.14.0 スコープ定義書

## 1. 文書概要

本書は、Growse v0.14.0で実装する外部Webサイト向けJavaScript実行、ECMAScript Modules、WebAssembly、iframe、Service Worker、Runtime sandbox、および通常サイト互換性の範囲、完了条件、対象外を定義する。

v0.14.0は、v0.13.0までのGo / JavaScript Dual Runtime、Tab単位Engine切り替え、DOM / Event / Scheduler / Fetch / Storage / Navigation API、複数Tab、HTTP Cache、Cookie / CORS、およびDevToolsが完成していることを前提とする。

本ReleaseはGrowse独自のHTML / CSS / JavaScript実装を拡張する。Chromium、WebKit、Gecko、WebView、Node.js、または既存ブラウザエンジンの埋め込みには切り替えない。

---

## 2. リリーステーマ

> **外部サイトのJavaScript、Module、WASM、iframe、Service Workerを隔離された実行環境へ載せ、Go / JavaScriptを切り替えながら現実のWebページを読み、動かし、診断できるブラウザへ。**

利用者はlocalhost専用fixtureだけでなく通常のHTTP(S)サイトを開き、JavaScript Engineを選んだTabで外部classic script、ECMAScript Module、WebAssembly、およびService Workerを実行できる。埋め込みFrameと親PageはOriginとsandbox属性に従って分離され、実行コードが停止、crash、過剰消費、または権限外操作を起こしてもBrowser本体と他Tabを巻き込まない。

Go Engineは既存WebGoとの互換性を維持し、Tab単位のGo / JS selectorと完全reloadによる切り替えを継続する。任意サイトが配信したGo sourceを暗黙実行せず、Go codeは明示的な`text/go`と利用者が選択したGo Engineでのみ実行する。

## 3. 準拠基準

- Script取得、classic / module実行順、`async` / `defer`、`DOMContentLoaded` / `load`、`document.readyState`はHTML Living Standardの該当algorithmを参考にする
- ECMAScript Moduleの解決、link、evaluate、namespace、およびdynamic `import()`はECMAScript Language SpecificationのModule semanticsを参考にする
- WebAssembly binary validationとexecutionはWebAssembly Core Specification 2.0、JavaScript APIはWebAssembly JavaScript Interfaceを参考にする
- iframe、nested browsing context、sandbox token、same-origin access、および`postMessage`はHTML Living Standardを参考にする
- Service Workerのregistration、install / activate、scope、fetch event、およびCache StorageはService Workers、Fetch、Cache specificationsを参考にする
- Runtime隔離は最小権限、default deny、brokered I/O、resource quota、crash containmentを脅威モデルとする
- DOM、URL、Event、CSSOM、およびHTML / CSS renderingは本書で列挙したWeb Platform APIとWPT caseを基準にする

仕様全体への適合や任意Webサイトの完全互換を宣言せず、本書の完了条件で観測可能な範囲に限定する。

## 4. 目標

1. JavaScript Engineを選んだ任意のHTTP(S) Pageで、inline / external classic scriptとECMAScript ModuleをBrowser規則に沿って取得・実行できる
2. WebAssembly、iframe、Service Workerを同じOrigin、Network、Storage、Page lifecycleへ接続できる
3. Go / JavaScript / WASMの実行をBrowser本体から分離し、権限、CPU、memory、件数、size、時間、IPCを強制上限内に閉じ込められる
4. 外部stylesheet、document base URL、代表的DOM / Event API、および動的mutationを通常サイトの描画へ反映できる
5. Tab単位Engine切り替え、複数Tab、History、DevTools、および既存WebGoアプリを回帰させない

## 5. Runtime workerとsandbox

### 5.1 Process境界

Go、JavaScript、およびWebAssembly codeはBrowser UI / Network / DOMを所有するProcess内で直接評価せず、Pageまたは分離単位ごとのRuntime worker processで実行する。Browserとworkerの通信はversion付き、長さ制限付きの型付きmessage protocolに限定し、生のGo pointer、Runtime object、filesystem path、environment variable、credential、Cookie、Authorization Headerを渡さない。

workerはBrowserがbrokerするDOM mutation、Event、Timer、Frame、Fetch、Storage、Navigation、Console、Module、WASM操作だけを要求できる。workerからの直接socket、DNS、filesystem、subprocess、dynamic library load、OS shell、およびBrowser内部package accessは公開しない。

workerの予期しない終了、protocol違反、panic、signal、timeout、およびoversized messageは対象PageのRuntime errorへ変換する。他TabとBrowser processを継続し、停止済みworkerのcallbackやmutationを受理しない。

### 5.2 資源上限

- workerはPage終了、Engine切り替え、Navigation、Service Worker停止で必ず終了させ、再利用時もOriginとgenerationを越えて状態を共有しない
- 1 Browser SessionあたりRuntime worker 32件、1 PageあたりFrame workerを含め16件までとする
- 1 IPC messageは1 MiB、1 workerの未処理messageは256件、Page全体の転送中payloadは8 MiBまでとする
- script / module評価は1 taskあたり既定5秒、worker停止猶予は1秒とし、超過時はinterrupt後にprocessを終了する
- JS heap、WASM linear memory、module graph、callback、listener、Timer、およびFetchには個別上限を設け、上限違反をPage単位で失敗させる
- Linux、macOS、Windowsでprocess boundaryとbrokered I/Oを適用し、利用可能なOS制約はplatform adapterで追加する。適用できない制約を安全なものとして偽装せずDevToolsへ状態を表示する

### 5.3 脅威モデル

v0.14.0における「完全なsandbox」とは、Growseが公開する実行機能について、実行コードがBrowser processのaddress space、Browser credential、任意filesystem、任意network、subprocessへ直接到達せず、すべてのhost作用が検証済みIPCとBrowser policyを通る状態を指す。

OS kernel、Go runtime、goja、WASM runtime、decoder、またはGrowse自身の未知の脆弱性まで存在しないとは宣言しない。sandbox無効化や縮退が発生した場合は外部codeを実行せず、明示的なerrorとしてfail closedする。

## 6. 外部JavaScriptとECMAScript Modules

### 6.1 外部Pageとclassic script

JavaScript Engineでは、最終Navigation URLがHTTP(S)であるPageのinline scriptを実行する。external classic scriptはsame-originとcross-originを取得でき、redirect後の最終URL、HTTP status、Content-Type、mixed content、credentials mode、integrity metadata、および安全上限を実行直前に再評価する。

Go Engineの`text/go`は既存互換を維持するが、外部Internet Originのsourceを自動実行しない。選択していないEngineのsourceは取得しない。

parser-blocking script、`defer` script、`async` scriptを区別する。parser-blockingとdeferは規定順、asyncは取得完了順に評価し、失敗した1 scriptをConsoleへ記録して後続の独立scriptとPage表示を継続する。

### 6.2 Document lifecycleとBrowser globals

`document.readyState`を`loading`、`interactive`、`complete`の順に遷移させる。defer / module完了後に`DOMContentLoaded`、asyncを含むload-blocking resource完了後に`load`を一度だけ配送する。Page cancel、Navigation、Engine切り替え後は古いlifecycle eventを配送しない。

`window`、`self`、`globalThis`、`document`、`location`、`history`、`navigator`、`origin`、`queueMicrotask`を同一Page globalへ接続する。browser globalとhost objectを別workerや別Originへ渡さない。

### 6.3 ECMAScript Modules

`<script type="module">`のinline / external graph、static `import` / `export`、re-export、namespace import、およびdynamic `import()`を扱う。Module URLはdocumentまたはreferrer moduleを基準に解決し、1 graph内では正規化URLごとに一度だけfetch、link、evaluateする。

Module fetchにはCORSを必須とし、redirect後Origin、JavaScript MIME、credentials、mixed contentを検査する。cycle、missing export、parse / link / evaluate error、dynamic import rejectionを対象Pageへ閉じ込める。

bare specifierは有効なimport mapにより解決された場合だけ受理する。document内で最初に有効なimport map 1件、mapping 1,024件、source 256 KiBを上限とし、Node.js / npm / CommonJS探索へfallbackしない。

Module graphは256 module、1 module 2 MiB、合計16 MiB、深さ64までとする。top-level awaitはworker taskをblockingせずPromise jobとして完了し、既定5秒で未完了ならgraphを失敗させる。

## 7. WebAssembly

### 7.1 JavaScript API

JavaScriptへ`WebAssembly.Module`、`Instance`、`Memory`、`Table`、`Global`、`compile`、`instantiate`、`validate`、`compileStreaming`、`instantiateStreaming`の本書で検証するsubsetを提供する。binaryはBrowser Fetch policyまたはJavaScriptの`ArrayBuffer` / typed arrayから受け取る。

import objectはJavaScript function、Memory、Table、Globalだけを明示的に渡し、WASI、filesystem、socket、clock、random、process environmentを暗黙提供しない。exported functionのtrapとhost callback errorはJavaScript exceptionへ変換する。

### 7.2 上限とlifecycle

1 module binaryは8 MiB、Page合計32 MiB、Module 32件、Instance 64件、Table 65,536 element、Memoryは初期64 MiB・最大256 MiBとする。memory最大値を省略したmoduleにもGrowse上限を適用する。

compile、instantiate、function callはworkerのtask timeoutとcancel対象にする。Page終了、Frame終了、Engine切り替え、およびworker停止後はWASM callback、memory、host functionを再利用しない。

## 8. iframeとNested Browsing Context

### 8.1 Frame lifecycleと描画

`<iframe src>`と`srcdoc`から子Documentを生成し、親Layoutの置換要素としてviewport、border box、clip、scrollを持たせる。Frame Navigation、reload、error表示、load event、Page closeを親Page generationへ結び付ける。

Frameは独立したDocument、History、Runtime worker、Event queue、Session Storage namespace、およびDevTools Page identityを持つ。同じBrowser SessionのCookie、HTTP Cache、Local Storageは既存Origin policyに従って共有する。

### 8.2 Origin、sandbox、通信

same-origin Frameだけが制限付き`contentWindow` / `contentDocument`へアクセスできる。cross-origin Frameはopaque proxyとしDOM、URL、Storage、Runtime objectを公開しない。

`sandbox`属性の空値、`allow-scripts`、`allow-same-origin`、`allow-forms`、`allow-popups`、`allow-top-navigation-by-user-activation`を扱い、未知tokenを無視する。許可のないscript、form、popup、top navigationは実行前に拒否する。

`window.parent`、`window.top`、`window.frames`、`postMessage`、`message` Eventを提供する。`targetOrigin`を送信時と配送時に検証し、message payloadは循環とsize上限を持つstructured clone subsetに限定する。

Frame深さ8、PageあたりFrame 32件、全Frame document合計32 MiB、1 message 1 MiB、未処理message 256件を上限とする。cycle、Navigation storm、親終了後callbackを安全に停止する。

## 9. Service Workerとoffline lifecycle

### 9.1 Registrationとlifecycle

Secure ContextのJavaScript Pageへ`navigator.serviceWorker.register()`、`getRegistration()`、`getRegistrations()`、`ready`、`controller`を提供する。localhostはSecure Contextとして扱う。

registrationはOriginとscopeで管理し、script URLはsame-originとする。install、waiting、activate、activated、redundantを順序付け、`skipWaiting()`、`clients.claim()`、`unregister()`を扱う。更新確認はHTTP Cacheを再検証し、byte-identical scriptでは不要な再installを行わない。

### 9.2 Fetch EventとCache Storage

active workerへscope内Navigation / Resource / Fetchの`fetch` Eventを配送し、同期的に呼ばれた`respondWith()`のResponseまたはnetwork fallbackを使用する。Service Worker自身のscript更新と内部fetchは無限再帰させない。

`caches.open()`、`match()`、`has()`、`delete()`、`keys()`と、Cacheの`match()`、`put()`、`delete()`、`keys()`を提供する。Request / Response bodyは複製可能なbuffered subsetとし、credentialを永続記録しない。

registration 64件、Originあたりactive worker 1件、Cache 32件、entry 4,096件、1 response 4 MiB、Origin合計128 MiB、install / activate / fetch event各5秒を上限とする。Browser再起動後もregistrationとCacheをprofileへ安全に復元し、破損entryをOrigin単位で隔離する。

Service WorkerはRuntime worker processで実行し、Pageが閉じてもpending eventの間だけ存続する。idle 30秒で停止し、次のeventで新しいworkerへ復元する。

## 10. 通常サイト向けDOM、Resource、Rendering互換性

### 10.1 Document URLとResource

最初の有効な`<base href>`をdocument base URLとして、anchor、form、classic / module script、stylesheet、CSS `url()`、iframe、Fetchの文字列URLへ一貫して適用する。無効URLと非HTTP(S) schemeは利用箇所のpolicyに従って拒否する。

HTTP(S)のcross-origin stylesheetとCSS `@import`をredirect後URL、MIME、mixed content、size / depth / count上限の下で適用する。stylesheet失敗は該当resourceだけを無効にし、残りのDocumentを描画する。

### 10.2 DOMとEvent

JavaScriptへ`querySelectorAll`、`createTextNode`、`getElementsByClassName`、`getElementsByTagName`、`append`、`prepend`、`removeChild`、`replaceChildren`、`children`、`parentElement`、`id`、`className`、`tagName`、`innerHTML`の安全なsubsetを追加する。

`classList.contains` / `toggle`、`removeEventListener`、Eventの`target` / `currentTarget` / `bubbles` / `cancelable` / `defaultPrevented`、`preventDefault()`、`stopPropagation()`を既存DOM / Event経路へ接続する。Mutation後にStyle、Layout、Hit Test、Inspectorを同じrevisionで再計算する。

### 10.3 対応する通常サイト範囲

外部stylesheet、Flex / Grid / Position / Background / Shadow / Transform、form control、image background、classic / module script、WASM、iframe、Service Workerを組み合わせた代表Pageを正しく描画・操作できることをIntegration TestとShowcaseで固定する。

v0.14.0で「通常サイト対応」と呼ぶ範囲は上記fixtureと選定WPTであり、未知の公開サイトが常に同一pixel、同一API、同一security behaviorで動作するという意味ではない。

## 11. DevToolsと利用者制御

ConsoleとNetworkへtop-level / Frame / Service Workerのcontext、classic / module / WASM種別、worker generation、sandbox状態、load / link / evaluate / trap / lifecycle errorを表示する。Response body、Header、Cookie、Authorization、Service Worker Cache body、およびIPC payloadは記録しない。

Browser chromeのGo / JS selectorはTab単位で維持する。Engine切り替えはtop-level Runtime、Frame Runtime、WASM Instance、Service Worker client connection、pending lifecycle eventを停止して完全reloadする。Service Worker registrationとOrigin Cacheはprofile stateとして保持するが、停止したPageのobjectやcallbackを新Engineへ共有しない。

sandboxが利用できない、worker executableの検証に失敗した、protocol versionが一致しない、またはOS制約の必須部分を適用できない場合、外部JavaScript / Go / WASMをfail closedし、UIとDevToolsへ理由を表示する。

## 12. テスト方針

- Unit Test: IPC codec、worker lifecycle、quota、script分類、Module解決、WASM wrapper、Frame origin / sandbox、Service Worker state machine、Cache、DOM APIを決定的に検証する
- Integration Test: 複数の`httptest` Originを使い、cross-origin classic / module / iframe、WASM、Service Worker interception、Engine切り替え、Navigation cancel、crash containmentを検証する
- Security Test: workerからのfilesystem / socket / subprocess / oversized IPCを拒否し、timeout、panic、kill、stale generationがBrowserと他Tabへ影響しないことを検証する
- Visual Regression: external-site fixture、nested Frame、dynamic DOM、Service Worker offline状態、およびDevTools contextをgoldenで固定する
- Conformance Test: HTML、ECMAScript、WebAssembly、Service Worker、DOM、CSSから本書に対応するWPT / specification caseを選定し、縮約点を記録する
- Platform Test: Linux、macOS、Windowsでworker起動、終了、crash回収、package同梱、sandbox capability reportingを検証する

実在サイト、外部API、公開DNS、時刻依存resourceをCIの合否条件には使用しない。外部サイト互換の手動確認先はcredential不要の静的test siteに限定し、自動Testは複数Originのoffline fixtureで再現する。

registration、update、install / activate、client control、fetch interception、Cache Storage、永続化、idle lifecycleを実装する。

## 17. Growse v0.14.0の定義

Growse v0.14.0とは、

> **Go / JavaScriptをTab単位で切り替えながら、外部HTTP(S)サイトのclassic scriptとECMAScript Modules、WebAssembly、iframe、Service Workerを、Browser本体から分離されたresource-bounded Runtime workerとOrigin policyの下で実行し、代表的な通常サイトのResource、DOM、Event、Layout、Paint、offline lifecycleを一貫して表示・操作・診断できるRelease。**

を満たすReleaseである。
