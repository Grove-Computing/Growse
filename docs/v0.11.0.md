# Growse v0.11.0 スコープ定義書

## 1. 文書概要

本書は、Growse v0.11.0 で実装する WebGo 向けの実用的なデータ通信 API、すなわち URL / HTTP Header / Form Data の値型、Fetch の中断・期限、および安全な Response 利用の範囲、完了条件、対象外を定義する。

v0.11.0 は、v0.10.0 までの Browser Session、複数 Tab、Page Lifecycle、WebGo Fetch、Cookie、Same-Origin Policy、CORS、Web Storage、HTTP Cache、Scheduler、URL / History API が完成していることを前提とする。

JavaScript、Service Worker、WebSocket、および既存ブラウザエンジンは使用しない。

---

## 2. リリーステーマ

> **WebGo アプリが API Request を安全に組み立て、期限付きで中断し、予測可能に Response を処理できるブラウザへ。**

利用者は、手作業で URL 文字列や Header map を組み立てず、URLSearchParams、Headers、FormData を使って API Request を構成できる。Request は Page 終了だけでなく利用者操作または期限超過で中断でき、成功・失敗・中断を区別して Page Event Queue 上で一度だけ受け取れる。Response は状態、URL、Header、JSON / text / binary body を安全な一回消費規則の下で扱える。

---

## 3. 準拠基準

- WHATWG URL Standard の URLSearchParams に関する serialize と application/x-www-form-urlencoded 処理
- Fetch Standard の Headers、Request、AbortSignal、network error、および body consumption の対応範囲
- HTML Living Standard の form data set と `multipart/form-data` / `application/x-www-form-urlencoded` の対応範囲
- RFC 9110 HTTP Semantics の field name、field value、および request method

JavaScript の `URL`、`Request`、`Response`、Promise、ReadableStream、Web IDL Interface をそのまま公開しない。仕様全体への適合は宣言せず、本書で明示した Go API と HTTP lifecycle の範囲に限定する。

---

## 4. 目標

1. WebGo から URL query、Header、Form body を順序と複数値を保って安全に構成できる
2. WebGo Fetch を明示的な cancel と timeout で停止し、失敗理由を区別できる
3. Response metadata と JSON / text / binary body を Page lifecycle と整合した一回消費 API で利用できる
4. 複数 Tab、CORS、Cookie、HTTP Cache、Page Event Queue の既存境界を弱めない
5. Request 数、URL / Header / Form / Body size、timeout、cancel 競合に安全上限を適用できる

---

## 5. Request Data API

### 5.1 URLSearchParams

WebGo へ `growse/url` Package を公開し、`URLSearchParams` 相当の Go 値型を提供する。少なくとも parse、append、set、get、get all、has、delete、entries、および encode を提供する。

値は insertion order と同一 key の複数値を保持する。encode は application/x-www-form-urlencoded の規則で UTF-8 を percent-encode し、空 key / 空 value を区別する。無効 UTF-8、size 上限超過、または不正な percent escape は値を部分更新せず error とする。

`navigation.Location` は不変のままとし、URLSearchParams の変更が現在 URL や History を暗黙に変更してはならない。変更を Navigation へ反映する場合は、既存の `navigation.Navigate`、`PushState`、または `ReplaceState` を明示的に呼ぶ。

### 5.2 Headers

`growse/fetch` の `Header` に代えて、順序と複数値を保持する `Headers` API を公開する。少なくとも append、set、get、values、has、delete、entries、および clone を提供する。

field name と value は HTTP の妥当性を検証し、制御文字、改行、または無効な name を拒否する。Host、Content-Length、Connection、Transfer-Encoding、Proxy-* など transport が所有する forbidden request header は WebGo から設定できない。Cookie は既存の Cookie Jar と credentials policy のみから付与し、WebGo Header で読み書きしない。Response の `Set-Cookie` も公開しない。

### 5.3 FormData と Request body

WebGo へ `growse/form` Package を公開し、`FormData` の field を append、set、get、get all、has、delete、entries できるようにする。v0.11.0 では field name / value と URL-encoded text body のみを対象とし、File、Blob、Directory、multipart upload は扱わない。

`fetch.Request` は JSON、text、bytes、URLSearchParams、FormData のうち一つだけを body として指定できる。複数指定は request を開始せず error callback を一度だけ配送する。body 型が Content-Type を明示しない場合は API が適切な Content-Type を設定し、明示値がある場合はそれを尊重する。

### 5.4 安全上限

- URL と encoded query は既存の 8 KiB URL 上限を超えない
- Header は request あたり最大 100 fields、各 name 256 bytes、各 value 8 KiB、合計 64 KiB とする
- FormData は最大 100 fields、各 name 256 bytes、各 value 64 KiB、encoded body 合計 1 MiB とする
- JSON、text、bytes body を含む request body は最大 1 MiB とする

上限超過、検証失敗、または encode 失敗時は Network Request、Cookie 更新、Cache 書込み、History 更新を行わず、対象 Fetch の失敗だけを配送する。

## 6. Fetch Control と Response API

### 6.1 Abort と timeout

WebGo へ `growse/fetch` の `AbortController` と read-only の `AbortSignal` を公開する。`Fetch` は任意の signal と timeout を受け取り、abort は同じ Request の network context、redirect、response body read、待機 callback を停止する。

利用者起因の abort、timeout、Page close、Tab close、Navigation supersede、Network failure は区別可能な stable error code と安全なメッセージで error callback へ配送する。abort 後または timeout 後に遅れて届いた response は Cookie、HTTP Cache、DOM、Storage、History を変更しない。成功と失敗の callback は Request ごとに高々一度、Page Event Queue 上でだけ実行する。

timeout は request 開始から response body を受け取り終えるまでを対象とし、0 は timeout 無効とする。signal が既に abort 済みなら network goroutine を開始しない。Page lifecycle による cancel は既存規則を維持し、利用者の abort で別 Fetch や別 Tab の処理を停止しない。

### 6.2 Response metadata と body

Response は status、status text、final URL、redirected、immutable Headers、および body size を公開する。final URL、error、log、status 表示に credential を含めない。

body は `Bytes`、`Text`、`JSON` の既存一回消費規則を維持し、`BodyUsed` で消費状態を参照できるようにする。JSON decode error、UTF-8 不正 text、size 超過、または二重消費は network error と区別し、Response 以外の Page state を変更しない。Response Header と body の値は caller が変更しても内部 network state を変えない defensive copy とする。

### 6.3 Fetch の公平性と lifecycle

Page あたりの in-flight Fetch は 16 件、Browser Session 全体では 128 件を既定上限とし、既存 Policy と整合させる。上限超過は新規 Request のみを失敗させる。abort、timeout、完了、Page close の競合は idempotent にし、goroutine、timer、response body、callback 参照を残さない。

Background Tab の Fetch は既存どおり完了可能だが、callback はその Tab の Page Event Queue へ直列配送する。active Tab への誤配送、閉じた Tab への callback、または background callback による active Tab の描画開始を許可しない。

## 7. テスト方針

- Unit Test: URLSearchParams、Headers、FormData、body encode、forbidden header、上限、abort、timeout、Response body の正常系・境界・失敗を fake clock と fake transport で検証する。
- Integration Test: fake HTTP Server と fake navigator を使い、CORS、Cookie、HTTP Cache、redirect、複数 Tab、Page close、Navigation supersede における Request / callback の隔離を検証する。
- Visual Regression: Data App Showcase の loading、cancel、timeout、HTTP error、JSON decode error 表示を固定 Viewport で検証する。
- Conformance Test: URL Standard、Fetch Standard、HTML Form の該当する WPT 由来テストを、Go API に翻訳して出典と差分を `docs/wpt.md` へ記録する。

---

## 8. Showcase

既存の Data App Showcase を拡張し、検索条件を URLSearchParams で生成し、FormData で新規 item を送信し、Headers で content negotiation を指定する。利用者は「読込を中止」と短い timeout を選べ、成功、HTTP status error、network error、cancel、timeout を互いに区別できる。

Showcase は test から起動する local fixture server のみを使用し、外部 Service、API key、Public Internet、実 Cookie、実 Profile を要求しない。

---

## 9. 実装フェーズ

### Phase 1 — Request Data API

- `growse/url` の URLSearchParams とテストを実装する
- `growse/fetch` の Headers と request header validation を実装する
- `growse/form` の FormData、body encoder、WebGo export を実装する
- Request size limits と CORS / Cookie 境界を検証する

### Phase 2 — Fetch Control と Response API

- AbortController、AbortSignal、timeout、error code を Fetch lifecycle へ統合する
- Response metadata、immutable Headers、BodyUsed と body decode failure を実装する
- multi-tab、Page lifecycle、HTTP Cache、Cookie の競合を integration test で検証する

### Phase 3 — 品質とリリース

- Data App Showcase、README、対応表、WPT 出典を更新する
- Unit、integration、visual regression、race、CI、成果物を検証する

---

## 10. v0.11.0 非対象

- WebSocket、Server-Sent Events、WebTransport、WebRTC
- Service Worker、Cache API、Background Sync、Push API、Notifications
- ReadableStream、WritableStream、upload / download progress、streaming request / response body
- File、Blob、Directory、multipart file upload、drag and drop
- JavaScript の URL、Request、Response、Promise、Web IDL Interface との API 互換性
- IndexedDB、Origin Private File System、File System Access API
- WebGo Runtime の完全な Sandbox 化、Process Sandbox、Site Isolation

---
